# Accessibility baseline (WCAG 2.2 AA)

The floor under every kit. Re-verify if `verified:` is more than 90 days old —
though WCAG success criteria move far more slowly than browser features, the
technique advice does not.

## The AA floor

| Requirement | Threshold |
|---|---|
| Body text contrast | ≥ 4.5:1 |
| Large text (≥24px, or ≥19px bold) | ≥ 3:1 |
| UI component and meaningful graphic edges | ≥ 3:1 |
| Target size (2.2, new) | 24×24 CSS px or an applicable spacing/other exception; 44×44 is an enhanced AAA/design target |
| Focus not obscured (2.2, new) | The focused element must not be hidden behind sticky headers/footers |
| Focus appearance | Visible indicator with sufficient contrast against adjacent colors |
| Dragging movements (2.2, new) | Any drag interaction needs a single-pointer alternative |
| Consistent help (2.2, new) | Help affordances stay in the same relative order across pages |
| Redundant entry (2.2, new) | Don't ask for the same information twice in one flow |
| Accessible authentication (2.2, new) | No cognitive-function test without an alternative (allow paste into OTP/password) |

## What 2.2 added that is commonly missed

The five criteria above marked "(2.2, new)" are the ones most often absent from
otherwise-accessible UI: sticky headers obscuring focus, drag-only reordering,
disabled paste on one-time-code fields, and 24px targets in dense tables.

## Focus

- Every interactive element has a visible `:focus-visible` style. Never
  `outline: none` without an equal or better replacement.
- Focus order follows reading order. Never use positive `tabindex`.
- Manage focus on route change, dialog open/close, and after destructive
  actions. `<dialog>` handles most of this — custom overlays do not.
- Check that sticky UI does not cover the focused element when tabbing.

## Names, roles, values

- Every control has an accessible name. Icon-only buttons need `aria-label`;
  an emoji or an icon glyph is not a name.
- Use the native element first (`<button>`, `<a href>`, `<input>`). ARIA is a
  repair, not a feature — a native control brings keyboard, focus and role for
  free.
- `aria-*` must reflect live state (`aria-expanded`, `aria-pressed`,
  `aria-current`, `aria-selected`).
- Follow the WAI-ARIA Authoring Practices pattern for any composite widget
  (menu, combobox, tabs, tree). Hand-invented keyboard models are a bug.

## Structure

- Use meaningful headings and order; one h1 is a useful page convention, not itself a WCAG criterion.
- Real landmarks; label them when repeated (`<nav aria-label="Pagination">`).
- Tables use `<th>` with `scope`; a layout table is a bug.
- Lists are lists. Don't fake them with divs.

## Motion & preferences

Respect, at minimum:

- `prefers-reduced-motion` — drop to opacity-only or instant. **Mandatory.**
- `prefers-color-scheme` — with a manual override available.
- `prefers-reduced-transparency`, `prefers-contrast`, `forced-colors` — check
  that the UI survives; borders often vanish in forced-colors mode.

## Async and dynamic content

- Announce async results with a live region (`aria-live="polite"`); errors with
  `role="alert"`.
- Loading state must be perceivable to screen readers, not only visually.
- Never trap focus outside of an intentional modal, and always provide escape.

## Meaning never by color alone

Pair every status color with an icon, a label, or a shape. This is a WCAG
requirement and it is also what keeps the UI legible in greyscale — the same
test `design-craft` uses for typographic hierarchy.

## Cheap verification pass

1. Tab through the whole screen. Can you reach and operate everything? Is the
   indicator always visible?
2. Test 200% text resize and 400% zoom/reflow equivalent to a 320 CSS px viewport. Anything cut off or scrolling
   horizontally?
3. Run the greyscale test — any information lost?
4. Check the longest real string in every field.
5. Turn on reduced motion and reload.

Automated checks leave manual and assistive-technology gaps. Record exactly
which keyboard, screen-reader and rendered checks were performed.
