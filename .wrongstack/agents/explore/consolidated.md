## Importer and Caller Tracing

- Resolve a module's full consumer set with two greps, always together: the bare module basename repo-wide, and the specifier pattern (e.g. `stores/<name>`, `components/<name>`). Sibling- and intra-directory consumers use relative specifiers (`./session-lanes`, `./session-lanes.js`, `./useChatViewState`) that specifier-pattern greps never match. Under `packages/webui/src`, the bare-basename grep plus `codebase-incoming-calls` resolves the full consumer set in one pass.
- Scope importer greps to the owning package path when a basename recurs across packages — `slash-commands/index.ts` exists in `packages/cli`, `packages/plug-lsp`, and `packages/telegram`, so an unscoped `grep slash-commands/index` returns 4+ cross-package false positives.
- Before mapping or editing any `project-server-*.ts` helper in `packages/tools/src/codebase-index/`, grep both the exported symbol names (`ServerQueryCaches`, `staleAwareRead`) and the module basename (`project-server-query-cache`). Some of these files are extraction drafts never wired into `project-server.ts`, which still carries the inline original; a symbol-only grep misses module-path imports and a module-path grep misses symbol imports.
- Trace `packages/core/src/storage/*` helpers by grepping the module basename first (e.g. `grep session-write-buffer`). These helpers typically have exactly one importer (`session-write-buffer.ts` ← `file-session-writer.ts`), so one hop plus a `new X` grep completes the dependency picture without broad exploration.
- For types-only modules (e.g. `packages/techstack/src/research/types.ts`), never derive the importer set from `codebase-incoming-calls` alone — it returns only importers of the queried symbols, so sibling files importing unqueried exports are missed. Pair symbol queries with a repo-wide module-path grep (`research/types(\.js)?['"]`) and a relative-form grep scoped to the owning directory (`from ['"]\./types(\.js)?['"]`), then check how cross-package consumers resolve it — they typically reach types through the package barrel (`from '@wrongstack/techstack'`), which deep-path greps never match.
- Disambiguate same-named services when tracing `incomingCallsService`, `outgoingCallsService`, `packageGraphService`, `fileGraphService`, or `symbolGraphService`: the sync implementations live in `packages/tools/src/codebase-index/index-service.ts`, while async shadowing wrappers with identical names are exported from `packages/tools/src/codebase-index/background-indexer.ts` and re-exported via the `./codebase-index/index` barrel. External consumers reach only the wrappers, never the sync originals.

## Tool Limitations

- Do not treat `codebase-incoming-calls` import/type_ref entries as call sites. Pair them with a targeted `read` of the constructor and producer methods to distinguish ownership (who creates the object) from usage (who feeds it).
- `codebase-incoming-calls` returns zero results for components wired via `React.lazy(() => import('./Name'))` in `packages/webui/src/components/view-registry.ts` — the dynamic import plus registry-object wiring is invisible to the call graph. Grep the bare component basename repo-wide and check `view-registry.ts` before concluding a WebUI component is dead code.
- Do not trust `codebase-skeleton` on import-dominated composition-root files (e.g. `packages/cli/src/slash-commands/index.ts`, which collapsed 215 lines to 1 at 99.6% "savings"). When the skeleton result looks degenerate, fall back to a full `read` before citing exports.

## Package-Specific Facts

- `@wrongstack/simpleui` grep hits are suspect until checked against `packages/cli/src/simpleui-dist.ts`: that file resolves the package by path string (`resolvePackageJson('@wrongstack/simpleui/package.json')`) for static-asset serving, so it looks like a barrel consumer but never imports the module. The simpleui barrel (`packages/simpleui/src/index.ts`) has zero in-repo importers by design — the package is consumed only as a built Vite `dist/` asset.
